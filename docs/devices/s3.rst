The S3 board
============

.. brief:
   Reader: a developer building or changing the firmware for the S3 AMOLED board.
   They already know: C, ESP-IDF basics, and the board comparison on the boards page.
   After this page they can: look up any S3 pin, bus, default or Kconfig value, and build and flash the S3.
   Page type: reference.

This page is the reference for the Waveshare ESP32-S3-Touch-AMOLED-1.75, the clock's default board.
It lists the hardware, the pin map, the build commands, the pre-configured defaults and every compile-time setting the S3 build uses.
The facts that shape the firmware most are near the top: the PSRAM cannot do DMA, the panel has no alpha channel, and the RTC alarm line reaches no wake input.

What the board is
-----------------

The ESP32-S3-Touch-AMOLED-1.75 is a 1.75-inch round capacitive-touch AMOLED development board.
It is the whole product.
The panel, the touch controller, the motion sensor and the real-time clock (RTC) all sit on the same small board and share the ESP32-S3's QSPI, I²C and I²S buses.
The clock body is a 3D-printed stand that holds the board and a battery (the panel render on the :doc:`start page <../index>`).

SoC and memory
~~~~~~~~~~~~~~

The ESP32-S3's FPU is what the bake uses (:doc:`the C core <../implementation/core-c>`).
``partitions.csv`` splits the 16 MB flash into four partitions:

- a 2 MB ``factory`` app partition;
- a 64 KB SPIFFS ``storage`` partition (credentials and alarm rules);
- a 2.5 MB ``moon_assets`` data partition with the equirectangular albedo and the int8 relief DEM;
- the ``moon_movie`` last row (11648 K, the chip's leftover), which holds the precomputed synodic boot movie (:doc:`the boot movie <../implementation/moon-movie>`).

The DEM's 2 MB size is what forced the 16 MB chip (:doc:`performance <../verification/performance>`).
The boot movie is 355 frames at 2 h spacing (``python -m moon.movie --target s3``).
A missing or stale movie never blocks a flash.

The S3's octal PSRAM is not SPI-DMA-capable.
Every DMA transfer the display stack makes must land in internal SRAM.
This one fact explains two settings that look arbitrary otherwise.
The LVGL flush strips are staged through internal RAM at 25 rows high, under the 32 KiB S3 SPI DMA cap (:doc:`the display pipeline <../implementation/display>`).
The 2 MB relief DEM lives in PSRAM and the CPU reads it; it is never sent by DMA.

The panel: CO5300 over QSPI
~~~~~~~~~~~~~~~~~~~~~~~~~~~

The CO5300 controller drives a 466×466 RGB565 (5-6-5, no alpha) AMOLED panel over QSPI.
Three properties matter to the rest of these docs.

The panel has no alpha channel.
Each pixel is on with an RGB565 color or off; there is no per-pixel transparency.
To fade out a screen, the firmware ramps the panel's hardware brightness register (0x51) instead of writing alpha.
:doc:`The display pipeline <../implementation/display>` and :doc:`the clock and sleep machine <../implementation/clock-sleep>` both rely on this.

Brightness is a register, not a backlight PWM.
The CO5300 has a per-panel brightness value.
The screen-switch fade to black and the light-sleep dim (:doc:`the clock and sleep machine <../implementation/clock-sleep>`) are slow writes to that register while the pixels stay constant.
That is why they are cheap.
It is also why a lost QSPI write shows up as a frozen frame, not a dimmed one (the GPSPI-stall incident, :doc:`on-device verification <../verification/device-verify>`).

The 466 panel draws the family's baseline type tier.
``components/ui/fonts/`` bakes the seven faces at 96/48/32 px (237 glyphs, 85 KiB of 4 bpp raster).
The P4 and knob tiers are the same faces re-baked at their panel ratios.
:ref:`The type sketch <type-family-ui>` draws the family, and :ref:`the glyph ladder <glyph-ladder-perf>` prices all three tiers.

Touch, motion and time
~~~~~~~~~~~~~~~~~~~~~~

The CST9217 capacitive touch controller sits on I²C.
The UI's input-device layer polls it.
The settings screens (:doc:`the round keyboard <../keyboard>`) and the clock-roll gesture (:doc:`the clock and sleep machine <../implementation/clock-sleep>`) both depend on it.

The QMI8658C IMU (accelerometer and gyro) sits on I²C and drives two behaviours that a photo does not show.
The tilt wake wakes the device when it leaves a settled pose.
The clock roll counter-rotates the clock face so it stays upright as you tilt the board.
Both are described in :doc:`the clock and sleep machine <../implementation/clock-sleep>`.
Both run on the 1 s monitor tick, not the chip's stream.
The firmware asks 86,400 times a day while the chip produces samples at its 1000 Hz output data rate, so the firmware reads one sample in a thousand (:ref:`the silicon ladder <silicon-ladder-perf>`).

The PCF85063A RTC sits behind a TCA9554 IO expander on I²C.
The RTC keeps the clock running through light sleep.
The product's deep sleep is app-level (backlight off, CPU still running), so the alarm still fires from the dark screen.
It fires by polling, not by a wake line.
The PCF's ALM output is wired to pin 3 of the TCA9554, and the running CPU reads that pin every 1.3 s (the ``lv_timer`` interrupt handler).
The firmware arms the alarm through the RTC's hardware alarm (``clock_clear_alarm`` and re-arm).
:doc:`The clock and sleep machine <../implementation/clock-sleep>` documents the bug where a stale armed ALM fired a phantom alarm, which is why a boot with zero rules disarms it.

Power
~~~~~

The board runs from USB in this build (the bench stand has a coiled cable in the photos).
The sleep machine (:doc:`the clock and sleep machine <../implementation/clock-sleep>`) exists because an always-on AMOLED on a desk draws power and risks burn-in.
Light sleep keeps the panel on but dims it.
Deep sleep turns the panel's backlight off.

The moon is shown static, so it burns faintly into the panel over weeks of always-on display.
This is an accepted trade-off: a faint burned-in moon is a feature, not a bug, and it is unlikely to make the display harder to read (:doc:`the animation pipelines <../implementation/animations>`, :doc:`/project/history`).

The board shim
~~~~~~~~~~~~~~

A vendored Waveshare BSP component (``components/esp32_s3_touch_amoled_1_75``) drives the board.
The project's own board logic sits in a thin shim, ``components/board``.
The shim (``board_display.c``) gives the rest of the code one ``board_panel()``, one ``board_panel_io()`` and one ``board_io_expander_init()`` that behave the same on the S3 and the P4.
The P4 has a different panel handle, no QSPI panel IO and no IO expander, so on the P4 the shim returns the P4 handle, NULL and NULL:

.. code-block:: c
   :caption: components/board/board_display.c (the whole shim)

   #include "board_display.h"

   esp_lcd_panel_handle_t board_panel(void) {
   #if defined(CONFIG_BOARD_P4)
       return bsp_display_get_panel_handle();
   #else
       return bsp_display_get_panel();
   #endif
   }

   esp_lcd_panel_io_handle_t board_panel_io(void) {
   #if defined(CONFIG_BOARD_P4)
       /* The P4's MIPI-DSI panel has no QSPI io; its drain witness is
        * S3-only, so this name only needs to LINK on the P4. */
       return NULL;
   #else
       return bsp_display_get_panel_io();
   #endif
   }

   esp_io_expander_handle_t board_io_expander_init(void) {
       /* The P4 board has no IO expander (no PCF85063A interrupt line). */
   #if defined(CONFIG_BOARD_P4)
       return NULL;
   #else
       return bsp_io_expander_init();
   #endif
   }

The panel's DMA staging, the 25-row flush-strip limit and the ``s_panel_mtx`` that serializes brightness writes are described in :doc:`the display pipeline <../implementation/display>` and :doc:`the clock and sleep machine <../implementation/clock-sleep>`.

The orange path is the wake-up caveat.
The RTC's ALM output lands on pin 3 of the TCA9554, which the running CPU polls every 1.3 s.
It is not wired to an ESP wake input, so a true ``esp_deep_sleep`` could never be woken by a timer or alarm on this board.
The product's deep sleep is app-level (backlight off, CPU still running), so the alarm still fires through that poll (:doc:`the clock and sleep machine <../implementation/clock-sleep>`).

The TF card socket
~~~~~~~~~~~~~~~~~~

The SD socket is SPI 1-bit: MOSI GPIO01, SCK GPIO02, MISO GPIO03, CS GPIO41, with D1–D7 not wired.
The board has no SDMMC wiring.

The TF hour cache (``UI_MOON_TFCACHE``, :doc:`the animation pipelines <../implementation/animations>`) mounts the card with ``esp_vfs_fat_sdspi_mount`` on SPI3_HOST.
It does not use the vendored BSP's ``bsp_sdcard_mount()``, because that attaches to SPI2_HOST.
SPI2 is already the QSPI panel's bus (``BSP_LCD_SPI_NUM``), and sharing it starves the card into a 0x107 timeout.
So ``moon_tfcache`` initializes the SPI3 bus itself (under the SDSPI contract the caller owns ``spi_bus_initialize``) and attaches the card there.
A missing card is a silent no-op, and the hourly refresh then bakes on the device.

The cache serves two producers: the hourly refresh, and the fallback leg of the boot replay (``UI_MOON_BOOT_REPLAY``, :doc:`the animation pipelines <../implementation/animations>`).
The boot replay plays the flash-resident boot movie first (:doc:`the boot movie <../implementation/moon-movie>`).
The card's stored hour frames play only when the movie is missing or its calcver is stale.
The card mounts lazily, on the first producer that runs.
With the boot replay on (the default), that is the movie-loop / card-fallback leg at boot, and only that leg pays the ~1 s SD probe.
With the replay off, the first hourly refresh mounts the card.

Build and flash
---------------

The S3 is the default target.
A plain ``idf.py build`` on a fresh clone (no ``sdkconfig``) configures ``esp32s3`` from ``sdkconfig.defaults``.
Before you start, identify the port and confirm the chip (:doc:`the board index <index>` has the procedure and the shared conventions).

.. code-block:: bash
   :caption: The S3 target (``<port>`` = the identified port; run ``esptool.py --port <port> chip_id`` first)

   source ~/esp/esp-idf/export.sh

   # moon assets (the NASA sources ship with the repo; the bake is
   # local, gitignored): first time = bake — own .venv (see the
   # getting-started page); re-bake alone after touching the asset
   # pipeline or MOON_ALBEDO_W:
   python3 assets/images/moon/get_assets.py --target s3
   cd assets/images/moon && .venv/bin/python -m moon.assets --target s3

   cd ../..
   idf.py build                          # default target = esp32s3
   # check the binary size against the 2048 K factory partition
   idf.py flash -p <port>                # app + storage SPIFFS + moon_assets + moon_movie
   idf.py monitor -p <port>              # serial console, 115200

Pre-configured defaults
-----------------------

The S3 build merges the shared defaults with ``sdkconfig.defaults.esp32s3``.
The build system appends the per-target file for ``IDF_TARGET=esp32s3``, and the later file wins.
The S3 file in full:

.. code-block:: text
   :caption: sdkconfig.defaults.esp32s3 (the S3-specific values)

   # S3-only defaults (auto-loaded after sdkconfig.defaults when
   # IDF_TARGET=esp32s3). Keep the shared file board-neutral.
   CONFIG_IDF_TARGET="esp32s3"
   # Flash size header: the S3's 16 MB chip (moved out of the shared
   # defaults 2026-11-25 when the P4 took its real 32 MB chip).
   CONFIG_ESPTOOLPY_FLASHSIZE_16MB=y
   # Octal PSRAM at 80 MHz: the S3's in-package 8 MB.
   CONFIG_SPIRAM_MODE_OCT=y
   CONFIG_SPIRAM_SPEED_80M=y
   # The S3 core clock (the P4 runs at its own 400 MHz default).
   CONFIG_ESP_DEFAULT_CPU_FREQ_MHZ_240=y
   # Task watchdog: core 1 runs the bounded moon bakes (the orbit re-bake,
   # the deferred re-bake and the once-per-hour producer -- each a
   # high-priority ~1.3-2.4 s full-disk-relief bake) plus the event day
   # scan; any of them can starve the CPU1 idle task for a full bake,
   # which would trip the 5 s WDT (log-only but noisy). The bakes are
   # bounded and self-cancelling, so a permanent core-1 hang is not a
   # realistic risk; core 0's idle check (IDF default, on) stays as the
   # hang safety net.
   CONFIG_ESP_TASK_WDT_CHECK_IDLE_TASK_CPU1=n
   # LCD flush queue depth 1: the S3 SPI DMA caps one transfer at 32 KiB
   # and PSRAM is not DMA-capable, so every strip is staged into internal
   # RAM; depth 1 keeps the peak internal allocation at one ~23 KB strip
   # (deeper queues exhausted the heap -> ESP_ERR_NO_MEM, see the vendored
   # BSP buffer_height 50->25 fix). S3 BSP symbol only.
   CONFIG_BSP_LCD_TRANS_QUEUE_DEPTH=1

This file has no ``CONFIG_BOARD_S3=y`` line.
The S3 is the default of the board ``choice`` (see `Board selection`_ below), so the default already selects it.
The P4 file does carry ``CONFIG_BOARD_P4=y``, to override that default.
The root ``CMakeLists`` target/board guard turns a stray board line in the wrong file into a build-time ``FATAL_ERROR``.

The shared file (``sdkconfig.defaults``) adds the board-neutral values:

- ``CONFIG_PARTITION_TABLE_CUSTOM=y`` (the S3 keeps the default ``partitions.csv``);
- ``CONFIG_SPIRAM=y``;
- ``CONFIG_FATFS_LFN_HEAP`` (FATFS long filenames, because the TF hour cache's hour keys exceed 8.3);
- the LVGL 9.6 setup, notably ``CONFIG_LV_USE_CLIB_MALLOC=y``: the clock roll's full-screen PSRAM transform layer needs the libc allocator, not LVGL's 64 KB static pool;
- the hardware brightness fade and the once-per-hour refresh (``CONFIG_UI_SCREEN_SWITCH_FADE=240``, ``CONFIG_UI_MOON_HOURLY_ENABLE=y``);
- ``CONFIG_UI_CLOCK_ALPHA_PCT=20``;
- ``CONFIG_LV_USE_SNAPSHOT=n`` (nothing on the device captures the screen).

The flash size header is per board: the S3 file sets the 16 MB header, the P4 file the 32 MB one.

Known limits
------------

- The ``factory`` partition is 2,097,152 bytes (2 MiB), the tightest budget of the three boards. Check the binary size after every build (:doc:`the binary-size chronology <../verification/binary>`).
- The octal PSRAM is not SPI-DMA-capable. Keep the BSP ``buffer_height`` at 25 and the flush queue depth at 1.
- The RTC's alarm line reaches no ESP wake input, so the board cannot wake from a true ``esp_deep_sleep``. Deep sleep is app-level, and the alarm fires through the 1.3 s poll.
- The panel has no alpha channel. Fades are brightness ramps on register 0x51.
- The static moon burns faintly into the AMOLED over time. This is an accepted trade-off; do not add anti-burn-in machinery without a fresh decision.
- The TF card must sit on SPI3_HOST, never the panel's SPI2_HOST.
