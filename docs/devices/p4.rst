The P4 4C port
==============

The second target is the **Waveshare ESP32-P4-WIFI6-Touch-LCD-XC**
("4C"): a 720×720 round IPS panel driven by a **JD9365** MIPI-DSI
controller, **GT911** touch, a remote **C6 Wi-Fi chip over SDIO**
(ESP-Hosted), 32 MB flash, and a 400 MHz quad-core RISC-V P4 core.
Porting to it was a full second board, not a configuration toggle —
the panel is a different *technology* (MIPI-DSI vs QSPI) with a
different controller, a different pixel format, and a different DMA
story. This page covers what the port took and what the
measurements showed.

**Panel-technology posture.** Burn-in is an AMOLED duty — and the
burn-in duty was consciously dropped on 2026-11-13, when the burn-in
spin subsystem was removed family-wide (the user's "non-amoled screens
(e.g. lcd) do not need to use the anti-burnin moon-spin animation"
came first; "lets completely remove the moon spin anti-burn-in"
followed the same day). On this IPS board there is no spin to run and
never was much need for one: the moon is the static LVGL frame. The
spin-era facts quoted on this page (the 103-row strips, the 1-FB +
``LV_DISPLAY_RENDER_MODE_NONE`` posture, the async-DMA reject
absorption) are the display-pipeline contract as measured when the
spin ran, kept as history; the ``UI_MOON_SPIN_*`` Kconfig symbols
were retired with the spin subsystem on 2026-11-13 (the config
sweep deleted the keys).

Component wiring
----------------

Like the S3, the 4C is a single board: the panel, the touch, and the
Wi-Fi all hang off the P4's peripheral buses, plus the ES8311 audio
codec. The overview below seals each bus into one box; the two
sketches after it open the bus bars (every GPIO number) and show the
key difference from the S3 in the wake-up story — **the board carries
no RTC IC and no IO expander**, so ``board_io_expander_init()``
returns ``NULL`` and the only wake source is a software ``esp_timer``
one-shot.

.. graphviz:: ../_graphs/p4-wiring.dot
   :alt: P4 component wiring overview
   :align: center
   :caption: The overview — one sealed box per bus: MIPI-DSI (JD9365 IPS), I²C (GT911 touch), SDIO (ESP32-C6 Wi-Fi via esp_hosted), I²S (ES8311 codec), plus the 32 MB flash budget and the 200 MHz PSRAM the DPI FIFO feeds; the green callout is the wake story the last sketch opens.

.. graphviz:: ../_graphs/p4-wiring-bus.dot
   :alt: P4 bus pin map
   :align: center
   :caption: The buses pin by pin — MIPI-DSI 2 data lanes at 1500 Mb/s, RGB888, to the JD9365 (backlight GPIO 26, RST GPIO 27); I²C SCL GPIO8 / SDA GPIO7 to the GT911, whose RST/INT sit at NC so the driver polls; SDIO to the ESP32-C6 (esp_hosted 1.4.7, esp_wifi_remote 0.14.5); I²S SCLK 12, MCLK 13, LCLK 10, DOUT 9 to the ES8311.

.. graphviz:: ../_graphs/p4-wiring-wake.dot
   :alt: P4 wake story
   :align: center
   :caption: The wake story — with no RTC and a NULL expander, only an esp_timer one-shot (a running CPU) can wake the board, so a pending alarm keeps the device in light sleep instead of the deep state.

The green box is the wake-up caveat: with no RTC and no expander, an
alarm can only be caught by a running CPU's ``esp_timer`` one-shot, so
while an alarm is pending the device deliberately stays in **light
sleep** (dim panel) instead of dropping to the deep state (backlight
off) — a deep-sleep wake does not exist on this board (:doc:`the clock and sleep machine <../implementation/clock-sleep>`).

TF card slot (hour cache)
-------------------------

The 4C also carries an onboard **microSD slot on its own 4-bit SDMMC
host** — separate from the Wi-Fi link: **CLK GPIO43, CMD GPIO44, D0–D3
GPIO39–42** (the official Waveshare ``08_SD_Card`` / ``05_sdmmc``
examples; callout #18 of the board's docs page). The registry BSP
exposes it as ``bsp_sdcard_mount()`` with exactly those pins
(``BSP_SD_*``, ``width = 4``) — the same call shape as the S3's 1-bit
socket — so the **TF hour cache** (``UI_MOON_TFCACHE``,
:doc:`the animation pipelines <../implementation/animations>`) serves
the hourly refresh symmetrically on both boards: the producer mounts the
card **lazily on the first producer to run** — with ``UI_MOON_BOOT_REPLAY``
on (the default) that is the boot replay task, which plays the stored
hour frames ascending and ends on the computed now-frame; with the
replay off boot never touches the SD bus — and every card failure falls
back silently to on-device baking. The module outlived the boot sweep
it was built for (retired 2026-11-13; the replay plays **stored**
frames, it computes none) and now caches one gray JPEG per hour,
pruned to the current synodic month at each new moon. The pins are disjoint from the C6's
SDIO link (CLK 18 / CMD 19 / D0–3 14–17); they are two different
SDMMC hosts, and the bench confirmed it: **Wi-Fi-connected + card
mounted** runs (2026-11-08) brought the card up at t≈40 s with the C6
link already at 4-bit/40 MHz — zero SDIO / esp_hosted / sdmmc errors.

Why a second board
------------------

The S3 AMOLED is the product's face, but its panel is 466×466 with a
25-row flush-strip ceiling (:doc:`the S3 board <s3>`). The P4's 720×720 panel makes
the same moon larger and, with the RISC-V cores, gives the bake real
headroom. The design goal for the port was:

- **The portable C core is shared verbatim.** No changes to
  ``components/moon/core`` — the same translation units compile for
  both targets. Board-specific differences live in the UI layer
  (panel scale, fonts, the DSI flush path) and the board shim.
- **One Kconfig board choice, three config files.**
  ``sdkconfig.defaults`` (shared) plus
  ``sdkconfig.defaults.esp32s3`` / ``sdkconfig.defaults.esp32p4``
  (per-target, auto-appended when present; later file wins). The P4
  build sets ``CONFIG_BOARD_P4=y`` from the per-target file; the root
  ``CMakeLists`` cross-checks the target against the board choice and
  fails the build with a ``FATAL_ERROR`` if they disagree.

Panel differences that matter to the pipeline
---------------------------------------------

.. list-table::
   :header-rows: 1
   :widths: 22 39 39

   * - Property
     - S3 (CO5300, QSPI)
     - P4 (JD9365, MIPI-DSI)
   * - Resolution
     - 466×466
     - 720×720
   * - Color
     - RGB565
     - RGB888
   * - Flush path
     - QSPI strip writes (25-row internal-RAM strips, 32 KiB DMA cap)
     - DSI async DMA (the async-DMA2D throughput floor shows up as "previous draw not finished" rejects, absorbed by the ``moon_panel_draw_wait`` retry — ~3,900 measured in the spin era — :doc:`the display pipeline <../implementation/display>`)
   * - Moon scale
     - MOON_PX 400, MOON_R 200
     - MOON_PX 650, MOON_R 325 (upscaled from 618/309 with the 2026-11-01 seam work)
   * - Teardown mode
     - n/a
     - 1-FB ``LV_COLOR_FORMAT`` single-buffer with ``LV_DISPLAY_RENDER_MODE_NONE`` (the 3-FB partial-mode scanout flip showed a stale spin pose from an old frame's last visit — the spin-era CCW flicker; the posture outlived the spin — :doc:`the display pipeline <../implementation/display>`)

The spin-era direct writes ran 103-row strips (the DPI FIFO underruns
at 206 on X16+XIP PSRAM), settled to 65 rows for the 650 px disk; that
write path retired with the spin subsystem (2026-11-13), and the
surviving strip pitch — ``MOON_STRIP_ROWS`` 130 — only *paces* the
LVGL invalidations the atomic displays use
(:doc:`the P4 port <../implementation/p4-port>`). The gray→RGB
conversion is an identity swap (888 panel, no 5-6-5 quantization) —
the art pass's warm LUT still applies because it is a *color* choice,
not a quantization artifact.

What the port took (M0–M4)
--------------------------

The port landed as a milestone sequence (the letters below are the
milestone labels used in the project's tracking):

- **M0 — bring-up**: board shim + board Kconfig + the 3-file
  sdkconfig split + ``partitions_p4.csv`` (9 MB ``factory``; the
  32 MB chip's header still says 16 MB, so esptool's size-mismatch
  warning is expected) + ``EXCLUDE_COMPONENTS`` per target + a
  separate gitignored ``dependencies.lock.p4`` (the P4's C6/esp_hosted
  dependency set differs from the S3's).
- **M1 — plumbing**: rev v1.3 board, PSRAM at 200 MHz, JD9365 + GT911
  + 32 MB all verified.
- **M2 — Wi-Fi**: the C6 over SDIO (esp_hosted 1.4.7,
  esp_wifi_remote 0.14.5): association + SNTP + AP scan verified.
- **M3 — moon @ 720**: board-conditional ``moon_ui.c`` (no new
  Kconfig): MOON_PX/MOON_R scaled, spin strips 103 rows, the
  ``--panel 720`` simulator path.
- **M4 — UI upscale**: ``ui_px.h`` scales ~70 literals in
  ``screens.c`` (S3 stays byte-identical at 466 via the
  ``--panel``-aware build); the P4 fonts (148/74/50 px) carry
  identical ``lv_font_t`` symbols selected by CMake on
  ``CONFIG_BOARD_P4`` (236 glyphs, 213 KiB of raster — the
  ``fonts_p4/`` tier also carries the clock icon U+F017 the S3's
  regular set lacks, because the P4 hub ring's 7th entry asks for
  it: :ref:`the type sketch <type-family-ui>`,
  :ref:`the glyph ladder <glyph-ladder-perf>`); the keep-mask
  (burn-in spin's UI mask) was re-derived on the upscaled arc.

M5 (clock degradation + manual time entry on P4) is the remaining
open firmware item as of this writing; the M6 docs milestone is the
Sphinx site this page belongs to.

Measured results on the P4
--------------------------

On-device captures (full run, 0 WDT / 0 panic; the boot sweep, the
dusk and the reject accounting are spin/sweep-era captures of now
retired subsystems, quoted as history):

- Boot sweep (retired 2026-11-13): 336/336 frames completed.
- Final bake: ~959 ms at 650 px (599 ms at the earlier 618 px scale,
  before the 2026-11-01 upscale).
- Dusk (retired 2026-11-13): ~43 s for the full constant-projection
  spin.
- The async-DMA rejects during the spin are absorbed — 0 dropped
  strips after the ``moon_panel_draw_wait`` retry (the retry rides
  today's atomic flushes on the same path).

After the 2026-11-04 clock rollers landed, the P4 binary is 1,605,984 B
(``0x188160``) — about 17 % of the 9 MB factory partition. The S3
binary at the same point is 1,511,280 B (``0x170f70``), about 72 % of
its 2 MB factory partition (the ~28 % headroom under the 2,097,152 B
ceiling; :doc:`the binary-size chronology <../verification/binary>` tracks the full binary-size chain).

Building and flashing the P4
----------------------------

The P4 is the second target: the build pins ``IDF_TARGET=esp32p4``
and keeps its own build directory (``build/p4``), its own
dependency lock (``dependencies.lock.p4``, gitignored — the S3 build
keeps ``dependencies.lock``) and its own live config (``sdkconfig.p4``,
gitignored — every P4 command carries ``-D SDKCONFIG=sdkconfig.p4``;
without it the P4 configure reads the root ``sdkconfig``, sees its
``IDF_TARGET=esp32s3`` pin and aborts in ``targets.cmake`` — "Target
… does not match currently selected IDF_TARGET". On a fresh clone the
flag creates ``sdkconfig.p4`` from the defaults split; afterwards it
also matches the ``build/p4`` cache entry, so keep passing it)
(:doc:`the board index <index>` for the shared conventions, the
sequential-build rule, and the port-identification procedure):

.. code-block:: bash
   :caption: The P4 target (``<port>`` = the identified port — run ``esptool.py --port <port> chip_id`` first)

   source ~/esp/esp-idf/export.sh

   # moon assets (all local, gitignored): first time = fetch + bake —
   # NASA sources sha256-pinned, own .venv (see the getting-started page);
   # re-bake alone after touching the asset pipeline or MOON_ALBEDO_W:
   python3 assets/images/moon/get_assets.py --target p4
   cd assets/images/moon && .venv/bin/python -m moon.assets --target p4

   cd ../..
   idf.py -D IDF_TARGET=esp32p4 -B build/p4 -D SDKCONFIG=sdkconfig.p4 build
   # check the binary size against the 9216 K factory partition
   # (the 32 MB chip carries a 16 MB binary header — esptool's
   # size-mismatch warning is expected)
   idf.py -D IDF_TARGET=esp32p4 -B build/p4 -D SDKCONFIG=sdkconfig.p4 flash -p <port>
   idf.py -D IDF_TARGET=esp32p4 -B build/p4 -D SDKCONFIG=sdkconfig.p4 monitor -p <port>

The first ``set-target esp32p4`` pulls the P4's component set (the
vendored 4C BSP; esp_hosted + esp_wifi_remote for the remote C6 over
SDIO, pinned in ``main/idf_component.yml``) — the three ``int``
``ESP_HOSTED_HOST_USB_*_MANIFEST`` guard keys
(:doc:`board selection <../reference/kconfig-board>`) keep the
component manager's version solver from aborting on that set.

Pre-configured defaults
-----------------------

The P4 build merges the shared defaults with
``sdkconfig.defaults.esp32p4`` (auto-appended for
``IDF_TARGET=esp32p4``, later file wins). The P4 file, in full:

.. code-block:: text
   :caption: sdkconfig.defaults.esp32p4 (the P4-specific values)

   # P4-only defaults (auto-loaded after sdkconfig.defaults when
   # IDF_TARGET=esp32p4). Values proven by the M0 scratch bring-up
   # (ESP32-P4-WIFI6-Touch-LCD-XC 4C, 2026-10-31) against IDF 5.5.1.
   CONFIG_IDF_TARGET="esp32p4"
   # Board select (see components/board/Kconfig.projbuild): the app's
   # P4-only code paths gate on CONFIG_BOARD_P4.
   CONFIG_BOARD_P4=y
   # Partition table: the shared defaults enable CONFIG_PARTITION_TABLE_CUSTOM;
   # IDF picks the CSV through the Kconfig value (the partition_table component's
   # project hook re-derives PARTITION_CSV_PATH from it, clobbering any plain
   # cmake set). The S3 keeps its default "partitions.csv" (2048K factory);
   # the P4 takes the 32 MB table with the 9216K factory.
   CONFIG_PARTITION_TABLE_CUSTOM_FILENAME="partitions_p4.csv"
   # Silicon: the attached board is rev v1.3 (legacy profile). 5.5.1 has no
   # ESP32P4_SELECTS_REV_LESS_V3 / REV_MIN_300 — 100..199 is the rev1_3 band.
   CONFIG_ESP32P4_REV_MIN_100=y
   CONFIG_BOOTLOADER_LOG_LEVEL_WARN=y
   CONFIG_BOOTLOADER_LOG_LEVEL=2
   CONFIG_ESPTOOLPY_FLASHMODE_QIO=y
   CONFIG_COMPILER_OPTIMIZATION_PERF=y
   # In-package PSRAM at 200 MHz (the rev v1.3 cap). SPIRAM_SPEED_200M is
   # gated on the experimental flag in 5.5.1 — without it the speed silently
   # falls back to 20 MHz (DSI underruns).
   CONFIG_SPIRAM_SPEED_200M=y
   CONFIG_SPIRAM_SPEED=200
   # Execute from PSRAM + the 256 KB L2 @ 128 B lines (M0 template values).
   CONFIG_SPIRAM_XIP_FROM_PSRAM=y
   CONFIG_CACHE_L2_CACHE_256KB=y
   CONFIG_CACHE_L2_CACHE_LINE_128B=y
   # The LVGL adapter task + the moon bakes want a taller main stack and a
   # 1000 Hz tick (the 1 ms task-delay floor resolves to real ticks).
   CONFIG_ESP_MAIN_TASK_STACK_SIZE=10240
   CONFIG_FREERTOS_HZ=1000
   CONFIG_FREERTOS_VTASKLIST_INCLUDE_COREID=y
   CONFIG_FREERTOS_GENERATE_RUN_TIME_STATS=y
   # Required by SPIRAM_SPEED_200M in 5.5.1 (see above).
   CONFIG_IDF_EXPERIMENTAL_FEATURES=y
   # The 4C panel (720x720). The 800x800 3.4C is CONFIG_BSP_LCD_TYPE_800_800_3_4_INCH.
   CONFIG_BSP_LCD_TYPE_720_720_4_INCH=y
   # ONE panel frame buffer (the BSP default is 3): with 3, the XC BSP's
   # TRIPLE_PARTIAL display start flips the continuous MIPI-DPI scanout
   # between the FBs on every LVGL refresh, so a partial (strip) flush can
   # land on the FB just after the scanout has moved to another -- showing a
   # half-updated surface (tearing). 1 FB + the adapter's NONE tear mode (set
   # in main.cpp) makes every LVGL strip write the single scanned surface;
   # the residual tearing is at most one frame, invisible at the LVGL refresh
   # rate. (The direct-write burn-in spin that first forced this is gone; the
   # setting stays as the panel's tear control.)
   CONFIG_BSP_LCD_DPI_BUFFER_NUMS=1
   # Remote C6 Wi-Fi over SDIO (M2): the esp_hosted / esp_wifi_remote pair
   # (component-manager deps, pinned in main/idf_component.yml). All SDIO
   # pins (CLK 18 / CMD 19 / D0-D3 14-17), the slave target (esp32c6), the
   # 4-bit @ 40 MHz bus and the slave reset (GPIO54) are esp_hosted
   # defaults that already match this board — the M0 bring-up associated
   # with none of them explicitly set. STA only (the app has no soft-AP
   # path): keep the slave's soft-AP buffers out.
   CONFIG_ESP_WIFI_SOFTAP_SUPPORT=n
   # The remote-side twin: esp_wifi_remote's injected Kconfig carries
   # WIFI_RMT_SOFTAP_SUPPORT (default y) and re-defaults the host's
   # ESP_WIFI_SOFTAP_SUPPORT from it — set both or the host one bounces back to y.
   CONFIG_WIFI_RMT_SOFTAP_SUPPORT=n
   # LVGL fast-math functions: XIP (PSRAM), NOT internal IRAM. The shared
   # sdkconfig.defaults sets LV_ATTRIBUTE_FAST_MEM_USE_IRAM=y for the S3, where
   # LVGL's esp.cmake maps LV_ATTRIBUTE_FAST_MEM to IRAM_ATTR = Xtensa .iram
   # (fast memory, a real win). On the P4 (RISC-V) IRAM_ATTR = .iram1.N, which
   # lands in the scarce internal sram_low and overflows the link (~113 KB of
   # LVGL in ~60 KB of headroom). The M0 known-good LVGL demo left it unset
   # (LVGL in XIP, ~2.6 KB IRAM) and ran clean; PSRAM XIP is proven here. The
   # P4 file is appended after the shared one, so this =n wins on esp32p4 and
   # the S3 keeps its IRAM fast-math. (Per-target override; see CLAUDE.md
   # "Kconfig n leaves the macro UNDEFINED" — this is a *defaults-file* value,
   # not a #define, so it is fine.)
   CONFIG_LV_ATTRIBUTE_FAST_MEM_USE_IRAM=n
   # Idle-task WDT, CPU1: the core-1 moon bakes (the boot bake, the orbit /
   # deferred re-bakes and the once-per-hour producer) can own one core for
   # seconds at a time (the first bake ~5-6 s at the 720 resolution); the idle
   # task on that core then cannot feed the 5 s WDT, so the check fires on
   # those bakes. Same treatment as the S3 (sdkconfig.defaults.esp32s3):
   # disable the CPU1 idle check only (CPU0 stays checked).
   CONFIG_ESP_TASK_WDT_CHECK_IDLE_TASK_CPU1=n
   # Clock: the 4C has no PCF85063A / IO expander — the external-RTC-IC path
   # (PCF registers for time/minute/countdown/alarm) is off. The time base is
   # the system clock over the crystal-backed internal RTC timer + SNTP; the
   # minute tick and the countdown/alarm arming run in software (esp_timer).
   # (Kconfig `n` leaves the macro UNDEFINED — the code gates on
   # #if CONFIG_CLOCK_USE_PCF85063A, which resolves false.)
   CONFIG_CLOCK_USE_PCF85063A=n
   # RTC clock source: the external 32 kHz crystal (the 4C mounts it, with a
   # VBAT battery header). The internal RC oscillator is only a few %
   # accurate and is unusable as a clock time base.
   CONFIG_RTC_CLK_SRC_EXT_CRYS=y

What the *live* ``sdkconfig.p4`` (the file ``-D SDKCONFIG=sdkconfig.p4``
selects) pins is what ``-B build/p4`` builds —
a stale line there shadows every defaults-file default; the built
binary's clock source is verified in ``build/p4/config/sdkconfig.h``,
and the bench-note lives in
:doc:`the clock and the sleep machine <../implementation/clock-sleep>`.

The other half of that core-1-bakes comment sits in the adapter
config: the S3 BSP pins the LVGL painter to core 0 itself
(``esp32_s3_touch_amoled_1_75.c:581-590``), while the P4 branch of
``main.cpp`` passes ``ESP_LV_ADAPTER_DEFAULT_CONFIG()`` through —
overriding only ``task_stack_size = 12288`` (:cfile:`main/main.cpp:558-570`)
— so the 4C's painter keeps the adapter default ``task_core_id = -1``,
"no affinity", and the producers' pinning alone carries the split on
this board. The affinity split, the spawn edges and the chip
interrogations of the whole crew are drawn in
:ref:`the crew sketch <task-roster-arch>`.

**The board line asymmetry, the P4 half:** this file **does** carry
``CONFIG_BOARD_P4=y`` — the Kconfig ``choice``'s default is the S3,
so selecting the P4 must override it, while the S3 file needs no
board line at all (:doc:`the S3 board <s3>`). The root
``CMakeLists`` target/board guard makes a stray board line in the
wrong file a build-time ``FATAL_ERROR``.

The shared file (``sdkconfig.defaults``) contributes the
board-neutral values: the 16 MB flash header
(``CONFIG_ESPTOOLPY_FLASHSIZE_16MB=y`` — both boards flash a 16 MB
header even though the P4's chip is 32 MB),
``CONFIG_PARTITION_TABLE_CUSTOM=y`` (the P4 file then selects
``partitions_p4.csv`` through
``CONFIG_PARTITION_TABLE_CUSTOM_FILENAME``), ``CONFIG_SPIRAM=y``,
``CONFIG_FATFS_LFN_HEAP`` (FATFS long filenames — the TF hour cache
hour keys exceed 8.3; a historic ``LFN_NONE`` pin was stripped from
the live configs),
the LVGL 9.6 setup (notably
``CONFIG_LV_ATTRIBUTE_FAST_MEM_USE_IRAM=y`` — which the P4 file
**flips to ``n``** above, because on the RISC-V P4 ``IRAM_ATTR``
would overflow the scarce ``sram_low``), and the same UI seeds the
S3 page lists. The P4's native bake size is not a Kconfig value at
all: it is ``#define MOON_PX 650`` (``components/ui/moon_ui.c``,
behind ``#if defined(CONFIG_BOARD_P4)``) — the old
``UI_MOON_ANIM_BAKE_PX`` Kconfig key was deleted with the sweep
2026-11-13.

---------------------
