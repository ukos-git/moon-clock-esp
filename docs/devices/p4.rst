The P4 4C port
==============

.. brief:
   Reader: a developer building or changing the firmware for the P4 4C board.
   They already know: C, ESP-IDF basics, the S3 board page.
   After this page they can: look up any P4 pin, default or Kconfig value, build and flash the P4, and see how it differs from the S3.
   Page type: reference.

This page is the reference for the Waveshare ESP32-P4-WIFI6-Touch-LCD-XC ("4C"), the clock's second board.
It lists the hardware, the wiring, the build commands, the pre-configured defaults and every compile-time setting the P4 build uses.
The P4 is a full port, not a configuration toggle: its panel uses a different technology (MIPI-DSI instead of QSPI), a different controller, a different pixel format and a different DMA path.
It also has no real-time clock (RTC) chip, so an alarm keeps the board in light sleep.

What the board is
-----------------

The 4C has a 720×720 round IPS panel driven by a JD9365 MIPI-DSI controller, GT911 touch, a remote ESP32-C6 Wi-Fi chip over SDIO (ESP-Hosted), 32 MB flash, and an ESP32-P4 with a 400 MHz dual-core RISC-V CPU.
Like the S3, it is a single board: the panel, the touch, the Wi-Fi and the ES8311 audio codec all hang off the P4's peripheral buses.

The S3 AMOLED is the product's face, but its panel is 466×466 with a 25-row flush-strip ceiling (:doc:`the S3 board <s3>`).
The P4's 720×720 panel shows the same moon larger, and the RISC-V cores give the bake real headroom.
The port follows two design rules:

- The portable C core is shared verbatim.
  ``components/moon/core`` has no P4 changes; the same translation units compile for both targets.
  Board differences live in the UI layer (panel scale, fonts, the DSI flush path) and in the board shim.
- One Kconfig board choice, three config files.
  ``sdkconfig.defaults`` (shared) plus ``sdkconfig.defaults.esp32s3`` / ``sdkconfig.defaults.esp32p4`` (per target, appended when present; the later file wins).
  The P4 build sets ``CONFIG_BOARD_P4=y`` from its per-target file.
  The root ``CMakeLists`` cross-checks the target against the board choice and stops the build with a ``FATAL_ERROR`` if they disagree.

The panel is IPS, so the AMOLED burn-in question does not arise.
The moon is the static LVGL frame on all boards.

Hardware summary
----------------

.. list-table::
   :header-rows: 1
   :widths: 26 74

   * - Part
     - What it is
   * - SoC
     - ESP32-P4, dual-core RISC-V at 400 MHz, board revision v1.3
   * - Memory
     - 32 MB flash; in-package PSRAM at 200 MHz with XIP and a 256 KB L2 cache
   * - Panel
     - JD9365, 720×720 RGB888 IPS over MIPI-DSI (2 data lanes at 1500 Mb/s)
   * - Touch
     - GT911, I²C
   * - Wi-Fi
     - ESP32-C6 over SDIO (esp_hosted 1.4.7, esp_wifi_remote 0.14.5), STA only
   * - Clock
     - no RTC chip, no IO expander: an external 32 kHz crystal (VBAT battery header) feeds the internal RTC timer, plus SNTP
   * - Audio
     - ES8311 codec, I²S
   * - Storage
     - microSD slot on its own 4-bit SDMMC host

How the panel differs from the S3's
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. list-table::
   :header-rows: 1
   :widths: 22 39 39

   * - Property
     - S3 (CO5300, QSPI)
     - P4 (JD9365, MIPI-DSI)
   * - Resolution
     - 466×466
     - 720×720
   * - Color
     - RGB565
     - RGB888
   * - Flush path
     - QSPI strip writes (25-row internal-RAM strips, 32 KiB DMA cap)
     - DSI async DMA. The async-DMA2D throughput floor shows up as "previous draw not finished" rejects, which the ``moon_panel_draw_wait`` retry absorbs (:doc:`the display pipeline <../implementation/display>`)
   * - Moon scale
     - MOON_PX 400, MOON_R 200
     - MOON_PX 650, MOON_R 325
   * - Tear control
     - n/a
     - 1-FB ``LV_COLOR_FORMAT`` single-buffer with ``LV_DISPLAY_RENDER_MODE_NONE``. With 3 frame buffers, the scanout flips between buffers and a partial flush can land on a buffer the scanout has left (:doc:`the display pipeline <../implementation/display>`)

``MOON_STRIP_ROWS`` is 130 on the P4.
It only paces the LVGL invalidations that the atomic frame displays use (:doc:`the P4 port <../implementation/p4-port>`).
The gray-to-RGB conversion is an identity swap, because the 888 panel has no 5-6-5 quantization.
The art pass's warm lookup table (LUT) still applies, because it is a color choice, not a quantization artifact.

The P4's bake size is not a Kconfig value.
It is ``#define MOON_PX 650`` in ``components/ui/moon_ui.c``, behind ``#if defined(CONFIG_BOARD_P4)``.

The UI scales to 720 through ``ui_px.h``, which scales about 70 literals in ``screens.c``.
The S3 stays byte-identical at 466 through the ``--panel``-aware build.
The P4 fonts (148/74/50 px) carry the same ``lv_font_t`` symbols, and CMake selects them on ``CONFIG_BOARD_P4`` (238 glyphs, 222 KiB of raster).
The ``fonts_p4/`` tier also carries the clock icon U+F017, which the S3's regular set lacks, because the 7th entry of the P4 hub ring uses it (:ref:`the type sketch <type-family-ui>`, :ref:`the glyph ladder <glyph-ladder-perf>`).

Measured on the device
~~~~~~~~~~~~~~~~~~~~~~

On-device captures ran clean (0 WDT, 0 panic):

- The final bake takes about 959 ms at 650 px.
- The async-DMA rejects are absorbed: 0 dropped strips after the ``moon_panel_draw_wait`` retry, which the atomic flushes use on the same path.

:doc:`The binary-size chronology <../verification/binary>` tracks the current P4 and S3 binary sizes.
Older captures (the boot sweep, the dusk, the spin-era rejects) are in :doc:`/project/history`.

Wiring and pin map
------------------

The overview below draws each bus as one closed box.
The two sketches after it open the bus bars (every GPIO number) and show the main difference from the S3 in the wake-up story.
The board carries no RTC IC and no IO expander, so ``board_io_expander_init()`` returns ``NULL`` and the only wake source is a software ``esp_timer`` one-shot.

.. graphviz:: ../_graphs/p4-wiring.dot
   :alt: The P4 board's parts grouped by bus: MIPI-DSI to the panel, I²C to touch, SDIO to the C6 Wi-Fi chip, I²S to the codec.
   :align: center
   :caption: One box per bus: MIPI-DSI (JD9365 IPS), I²C (GT911 touch), SDIO (ESP32-C6 Wi-Fi via esp_hosted), I²S (ES8311 codec), plus the 32 MB flash budget and the 200 MHz PSRAM that feeds the DPI FIFO. The green callout is the wake path that the last sketch opens.

.. graphviz:: ../_graphs/p4-wiring-bus.dot
   :alt: The P4 buses drawn pin by pin, with every GPIO number.
   :align: center
   :caption: The buses pin by pin. MIPI-DSI: 2 data lanes at 1500 Mb/s, RGB888, to the JD9365 (backlight GPIO 26, RST GPIO 27). I²C: SCL GPIO8, SDA GPIO7 to the GT911, whose RST and INT are NC, so the driver polls. SDIO to the ESP32-C6 (esp_hosted 1.4.7, esp_wifi_remote 0.14.5). I²S: SCLK 12, MCLK 13, LCLK 10, DOUT 9 to the ES8311.

.. graphviz:: ../_graphs/p4-wiring-wake.dot
   :alt: The P4 wake path: with no RTC and no expander, only an esp_timer one-shot can wake the board.
   :align: center
   :caption: The wake path. With no RTC and a NULL expander, only an esp_timer one-shot on a running CPU can wake the board, so a pending alarm keeps the device in light sleep instead of the deep state.

The green box is the wake-up caveat.
With no RTC and no expander, only a running CPU's ``esp_timer`` one-shot can catch an alarm.
So while an alarm is pending, the device stays in light sleep (dim panel) instead of dropping to the deep state (backlight off).
This board has no deep-sleep wake (:doc:`the clock and sleep machine <../implementation/clock-sleep>`).

The C6 SDIO link uses CLK 18, CMD 19, D0–D3 14–17, the slave reset on GPIO54, and a 4-bit bus at 40 MHz.
All of these are esp_hosted defaults that match the board.

The TF card slot
~~~~~~~~~~~~~~~~

The 4C has an onboard microSD slot on its own 4-bit SDMMC host, separate from the Wi-Fi link.
Its pins are CLK GPIO43, CMD GPIO44 and D0–D3 GPIO39–42 (the official Waveshare ``08_SD_Card`` / ``05_sdmmc`` examples; callout #18 of the board's docs page).
The registry BSP exposes it as ``bsp_sdcard_mount()`` with those pins (``BSP_SD_*``, ``width = 4``), the same call shape as the S3's 1-bit socket.

So the TF hour cache (``UI_MOON_TFCACHE``, :doc:`the animation pipelines <../implementation/animations>`) works the same on both boards.
It caches one gray JPEG per hour and prunes to the current synodic month at each new moon.
It serves the hourly refresh, and it is the fallback leg of the boot replay (``UI_MOON_BOOT_REPLAY``): the boot replay plays the flash-resident boot movie first (:doc:`the boot movie <../implementation/moon-movie>`) and uses the card's stored hour frames only when the movie is missing or calcver-stale.
The card mounts lazily on the first producer that runs.
Every card failure falls back silently to baking on the device.

The card pins are disjoint from the C6's SDIO link (CLK 18 / CMD 19 / D0–3 14–17); the two are different SDMMC hosts.
The bench confirmed it: runs with Wi-Fi connected and the card mounted brought the card up at t≈40 s with the C6 link already at 4-bit/40 MHz, with zero SDIO, esp_hosted or sdmmc errors.

Build and flash
---------------

The P4 build pins ``IDF_TARGET=esp32p4`` and keeps three things of its own:

- the build directory ``build/p4``;
- the dependency lock ``dependencies.lock.p4`` (gitignored; the S3 build keeps ``dependencies.lock``);
- the live config ``sdkconfig.p4`` (gitignored).

Every P4 command carries ``-D SDKCONFIG=sdkconfig.p4``.
Without it, the P4 configure reads the root ``sdkconfig``, sees its ``IDF_TARGET=esp32s3`` pin and aborts in ``targets.cmake`` with "Target … does not match currently selected IDF_TARGET".
On a fresh clone the flag creates ``sdkconfig.p4`` from the defaults split.
After that it also matches the ``build/p4`` cache entry, so keep passing it.

Before you start, identify the port and confirm the chip (:doc:`the board index <index>` has the procedure, the sequential-build rule and the shared conventions).

.. code-block:: bash
   :caption: The P4 target (``<port>`` = the identified port; run ``esptool.py --port <port> chip_id`` first)

   source ~/esp/esp-idf/export.sh

   # moon assets (the NASA sources ship with the repo; the bake is
   # local, gitignored): first time = bake — own .venv (see the
   # getting-started page); re-bake alone after touching the asset
   # pipeline or MOON_ALBEDO_W:
   python3 assets/images/moon/get_assets.py --target p4
   cd assets/images/moon && .venv/bin/python -m moon.assets --target p4

   cd ../..
   idf.py -D IDF_TARGET=esp32p4 -B build/p4 -D SDKCONFIG=sdkconfig.p4 build
   # check the binary size against the 9216 K factory partition
   idf.py -D IDF_TARGET=esp32p4 -B build/p4 -D SDKCONFIG=sdkconfig.p4 flash -p <port>
   idf.py -D IDF_TARGET=esp32p4 -B build/p4 -D SDKCONFIG=sdkconfig.p4 monitor -p <port>

The first ``set-target esp32p4`` pulls the P4's component set: the vendored 4C BSP, and esp_hosted + esp_wifi_remote for the remote C6 over SDIO, pinned in ``main/idf_component.yml``.
The three ``int`` ``ESP_HOSTED_HOST_USB_*_MANIFEST`` guard keys (:doc:`board selection <../reference/kconfig-board>`) keep the component manager's version solver from aborting on that set.

Pre-configured defaults
-----------------------

The P4 build merges the shared defaults with ``sdkconfig.defaults.esp32p4``.
The build system appends the per-target file for ``IDF_TARGET=esp32p4``, and the later file wins.
The P4 file in full:

.. code-block:: text
   :caption: sdkconfig.defaults.esp32p4 (the P4-specific values)

   # P4-only defaults (auto-loaded after sdkconfig.defaults when
   # IDF_TARGET=esp32p4). Values proven by the M0 scratch bring-up
   # (ESP32-P4-WIFI6-Touch-LCD-XC 4C, 2026-10-31) against IDF 5.5.1.
   CONFIG_IDF_TARGET="esp32p4"
   # Board select (see components/board/Kconfig.projbuild): the app's
   # P4-only code paths gate on CONFIG_BOARD_P4.
   CONFIG_BOARD_P4=y
   # Partition table: the shared defaults enable CONFIG_PARTITION_TABLE_CUSTOM;
   # IDF picks the CSV through the Kconfig value (the partition_table component's
   # project hook re-derives PARTITION_CSV_PATH from it, clobbering any plain
   # cmake set). The S3 keeps its default "partitions.csv" (2048K factory);
   # the P4 takes the 32 MB table with the 9216K factory.
   CONFIG_PARTITION_TABLE_CUSTOM_FILENAME="partitions_p4.csv"
   # Flash size header: the P4's REAL 32 MB chip (bumped from the inherited
   # 16 MB header 2026-11-25). The 16 MB header was a shared-defaults
   # leftover; the esptool size-mismatch warning it caused is gone -- the
   # header now matches the hardware, and the partition table (the
   # moon_movie LAST row) can use the whole 32 MB.
   CONFIG_ESPTOOLPY_FLASHSIZE_32MB=y
   # Silicon: the attached board is rev v1.3 (legacy profile). 5.5.1 has no
   # ESP32P4_SELECTS_REV_LESS_V3 / REV_MIN_300 — 100..199 is the rev1_3 band.
   CONFIG_ESP32P4_REV_MIN_100=y
   CONFIG_BOOTLOADER_LOG_LEVEL_WARN=y
   CONFIG_BOOTLOADER_LOG_LEVEL=2
   CONFIG_ESPTOOLPY_FLASHMODE_QIO=y
   CONFIG_COMPILER_OPTIMIZATION_PERF=y
   # In-package PSRAM at 200 MHz (the rev v1.3 cap). SPIRAM_SPEED_200M is
   # gated on the experimental flag in 5.5.1 — without it the speed silently
   # falls back to 20 MHz (DSI underruns).
   CONFIG_SPIRAM_SPEED_200M=y
   CONFIG_SPIRAM_SPEED=200
   # Execute from PSRAM + the 256 KB L2 @ 128 B lines (M0 template values).
   CONFIG_SPIRAM_XIP_FROM_PSRAM=y
   CONFIG_CACHE_L2_CACHE_256KB=y
   CONFIG_CACHE_L2_CACHE_LINE_128B=y
   # The LVGL adapter task + the moon bakes want a taller main stack and a
   # 1000 Hz tick (the 1 ms task-delay floor resolves to real ticks).
   CONFIG_ESP_MAIN_TASK_STACK_SIZE=10240
   CONFIG_FREERTOS_HZ=1000
   CONFIG_FREERTOS_VTASKLIST_INCLUDE_COREID=y
   CONFIG_FREERTOS_GENERATE_RUN_TIME_STATS=y
   # Required by SPIRAM_SPEED_200M in 5.5.1 (see above).
   CONFIG_IDF_EXPERIMENTAL_FEATURES=y
   # The 4C panel (720x720). The 800x800 3.4C is CONFIG_BSP_LCD_TYPE_800_800_3_4_INCH.
   CONFIG_BSP_LCD_TYPE_720_720_4_INCH=y
   # ONE panel frame buffer (the BSP default is 3): with 3, the XC BSP's
   # TRIPLE_PARTIAL display start flips the continuous MIPI-DPI scanout
   # between the FBs on every LVGL refresh, so a partial (strip) flush can
   # land on the FB just after the scanout has moved to another -- showing a
   # half-updated surface (tearing). 1 FB + the adapter's NONE tear mode (set
   # in main.cpp) makes every LVGL strip write the single scanned surface;
   # the residual tearing is at most one frame, invisible at the LVGL refresh
   # rate. (The direct-write burn-in spin that first forced this is gone; the
   # setting stays as the panel's tear control.)
   CONFIG_BSP_LCD_DPI_BUFFER_NUMS=1
   # Remote C6 Wi-Fi over SDIO (M2): the esp_hosted / esp_wifi_remote pair
   # (component-manager deps, pinned in main/idf_component.yml). All SDIO
   # pins (CLK 18 / CMD 19 / D0-D3 14-17), the slave target (esp32c6), the
   # 4-bit @ 40 MHz bus and the slave reset (GPIO54) are esp_hosted
   # defaults that already match this board — the M0 bring-up associated
   # with none of them explicitly set. STA only (the app has no soft-AP
   # path): keep the slave's soft-AP buffers out.
   CONFIG_ESP_WIFI_SOFTAP_SUPPORT=n
   # The remote-side twin: esp_wifi_remote's injected Kconfig carries
   # WIFI_RMT_SOFTAP_SUPPORT (default y) and re-defaults the host's
   # ESP_WIFI_SOFTAP_SUPPORT from it — set both or the host one bounces back to y.
   CONFIG_WIFI_RMT_SOFTAP_SUPPORT=n
   # LVGL fast-math functions: XIP (PSRAM), NOT internal IRAM. The shared
   # sdkconfig.defaults sets LV_ATTRIBUTE_FAST_MEM_USE_IRAM=y for the S3, where
   # LVGL's esp.cmake maps LV_ATTRIBUTE_FAST_MEM to IRAM_ATTR = Xtensa .iram
   # (fast memory, a real win). On the P4 (RISC-V) IRAM_ATTR = .iram1.N, which
   # lands in the scarce internal sram_low and overflows the link (~113 KB of
   # LVGL in ~60 KB of headroom). The M0 known-good LVGL demo left it unset
   # (LVGL in XIP, ~2.6 KB IRAM) and ran clean; PSRAM XIP is proven here. The
   # P4 file is appended after the shared one, so this =n wins on esp32p4 and
   # the S3 keeps its IRAM fast-math. (Per-target override; see CLAUDE.md
   # "Kconfig n leaves the macro UNDEFINED" — this is a *defaults-file* value,
   # not a #define, so it is fine.)
   CONFIG_LV_ATTRIBUTE_FAST_MEM_USE_IRAM=n
   # Idle-task WDT, CPU1: the core-1 moon bakes (the boot bake, the orbit /
   # deferred re-bakes and the once-per-hour producer) can own one core for
   # seconds at a time (the first bake ~5-6 s at the 720 resolution); the idle
   # task on that core then cannot feed the 5 s WDT, so the check fires on
   # those bakes. Same treatment as the S3 (sdkconfig.defaults.esp32s3):
   # disable the CPU1 idle check only (CPU0 stays checked).
   CONFIG_ESP_TASK_WDT_CHECK_IDLE_TASK_CPU1=n
   # Clock: the 4C has no PCF85063A / IO expander — the external-RTC-IC path
   # (PCF registers for time/minute/countdown/alarm) is off. The time base is
   # the system clock over the crystal-backed internal RTC timer + SNTP; the
   # minute tick and the countdown/alarm arming run in software (esp_timer).
   # (Kconfig `n` leaves the macro UNDEFINED — the code gates on
   # #if CONFIG_CLOCK_USE_PCF85063A, which resolves false.)
   CONFIG_CLOCK_USE_PCF85063A=n
   # RTC clock source: the external 32 kHz crystal (the 4C mounts it, with a
   # VBAT battery header). The internal RC oscillator is only a few %
   # accurate and is unusable as a clock time base.
   CONFIG_RTC_CLK_SRC_EXT_CRYS=y

What ``-B build/p4`` builds is what the live ``sdkconfig.p4`` pins (the file that ``-D SDKCONFIG=sdkconfig.p4`` selects).
A stale line there shadows every defaults-file default.
You can verify the built binary's clock source in ``build/p4/config/sdkconfig.h``; the bench note is in :doc:`the clock and the sleep machine <../implementation/clock-sleep>`.

The watchdog comment above has a second half in the LVGL adapter config.
The S3 BSP pins the LVGL painter to core 0 itself (:cfile:`components/esp32_s3_touch_amoled_1_75/esp32_s3_touch_amoled_1_75.c:581-590`).
The P4 branch of ``main.cpp`` passes ``ESP_LV_ADAPTER_DEFAULT_CONFIG()`` through and overrides only ``task_stack_size = 12288`` (:cfile:`main/main.cpp:558-570`).
So the 4C's painter keeps the adapter default ``task_core_id = -1`` ("no affinity"), and on this board the producers' pinning alone carries the split.
:ref:`The crew sketch <task-roster-arch>` draws the affinity split, the spawn edges and the chip queries of all the tasks.

This file carries ``CONFIG_BOARD_P4=y``.
The Kconfig ``choice`` defaults to the S3, so selecting the P4 must override it, while the S3 file needs no board line at all (:doc:`the S3 board <s3>`).
The root ``CMakeLists`` target/board guard turns a stray board line in the wrong file into a build-time ``FATAL_ERROR``.

The shared file (``sdkconfig.defaults``) adds the board-neutral values:

- ``CONFIG_PARTITION_TABLE_CUSTOM=y`` (the P4 file then selects ``partitions_p4.csv`` through ``CONFIG_PARTITION_TABLE_CUSTOM_FILENAME``);
- ``CONFIG_SPIRAM=y``;
- ``CONFIG_FATFS_LFN_HEAP`` (FATFS long filenames, because the TF hour cache's hour keys exceed 8.3);
- the LVGL 9.6 setup, notably ``CONFIG_LV_ATTRIBUTE_FAST_MEM_USE_IRAM=y``, which the P4 file sets to ``n`` above because on the RISC-V P4 ``IRAM_ATTR`` would overflow the scarce ``sram_low``;
- the same UI seeds the S3 page lists.

The flash size header is per board: the P4 file sets the real 32 MB header, the S3 file the 16 MB one.

Known limits
------------

- The board has no RTC chip and no deep-sleep wake. A pending alarm keeps it in light sleep.
- Time depends on SNTP and the 32 kHz crystal. The fallback for a clock that cannot sync is the manual time entry screen (:doc:`/ui/settings-time`), opened by the settings hub's clock icon and reachable only on the P4.
- The board has no motion sensor, so there is no tilt wake and no clock roll.
- Every P4 command needs ``-D SDKCONFIG=sdkconfig.p4``; without it the configure aborts.
- ``CONFIG_LV_ATTRIBUTE_FAST_MEM_USE_IRAM`` must stay ``n`` on the P4, or the link overflows ``sram_low``.
- PSRAM at 200 MHz needs ``CONFIG_IDF_EXPERIMENTAL_FEATURES=y``; without it the speed falls back to 20 MHz and the DSI underruns.
